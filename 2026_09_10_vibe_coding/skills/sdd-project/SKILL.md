# sdd-project — פרויקט משותף לאנשים וסוכנים, לפי Spec Driven Development

## מה הסקיל עושה

שני מצבים. זהה איזה מהם מתאים לפי מצב התיקייה:

| מצב | מתי | מה עושים |
|---|---|---|
| **A. הקמה** | תיקייה ריקה, או תיקייה בלי `AGENTS.md` + `specs/` | סעיף "הקמת פרויקט" |
| **B. עבודה** | יש כבר `AGENTS.md`, `specs/`, `plans/`, `issues/`, `progress/` | סעיף "עבודה בפרויקט קיים" |

בדיקה מהירה: `ls AGENTS.md specs plans issues progress docs 2>/dev/null`.

## העיקרון שהסקיל משרת

בפרויקט עובדים כמה בני אדם וכמה סוכנים במקביל. אף אחד לא רואה את הצ׳אט
של האחר, וסוכן לא זוכר את הסשן הקודם. שני כללים מחזיקים את זה:

1. **מה שלא כתוב במסמך — לא קרה.** כל בקשה, החלטה, הנחה וסירוב מהצ׳אט
   נכתבים למסמך לפני שהסשן מסתיים
2. **אין קוד בלי spec מאושר.** לפני שיוצרים מערכת, קוד או רכיב תוכנה,
   כותבים תיאור ותיעוד של הדרישות ממנו, ואדם מאשר

הזרימה הקבועה:

```text
issues/  →  specs/  →  plans/  →  קוד + בדיקות  →  docs/journal/  →  progress/
 הבעיה      הדרישות     הדרך         הביצוע           מה נעשה         איפה זה עומד
```

## A. הקמת פרויקט

### 1. אסוף את הפרמטרים

מ-`$ARGUMENTS`, מהשיחה, או שאל. ארבעה חובה, השאר עם ברירת מחדל:

| פרמטר | חובה | מקור |
|---|---|---|
| תיקיית יעד | כן | `$0` או התיקייה הנוכחית |
| `--name` שם הפרויקט | כן | מהבקשה |
| `--owner` בעל/ת הפרויקט | כן | שם המשתמש |
| `--request` ציטוט הבקשה | כן | **ההודעה של המשתמש, בלשונו.** לא פרפרזה |
| `--agent-id` | לא | `claude/<owner>` |
| `--tool`, `--model` | לא | הכלי והמודל שאתה רץ בהם |
| `--description` | לא | משפט אחד מהבקשה |
| `--date` | לא | היום |

אל תשאל על מה שאפשר להסיק. שאל רק אם חסר שם פרויקט או בעלים.

### 2. הרץ את הסקריפט

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/scaffold.py" <target> \
  --name "<שם>" --owner "<בעלים>" --request "<ציטוט>" \
  --agent-id claude/<owner> --tool "Claude Code" --model "<המודל שלך>"
```

הסקריפט אינו דורס קבצים קיימים. הפלט התקין: רשימת `+` של 27 קבצים, בלי
שורת "אזהרה: נשארו placeholders". אם יש קבצים שדולגו (`=`), דווח עליהם
ואל תוסיף `--force` בלי שהאדם ביקש.

### 3. השלם מה שהסקריפט לא יכול לדעת

פתח `docs/sessions/<date>-01-project-setup.md` ומלא את סעיף **"הנחות
שהסוכן הניח בלי לשאול"**: כל דבר שהחלטת לבד — שם, מיקום, מזהה סוכן, כלל
ה-Git. סעיף ריק כאן הוא כישלון של הסקיל.

אם המשתמש ציין פרטים על הפרויקט (מה בונים, מי בצוות, אילו כלים) — הוסף
אותם ל-`README.md` ול-`docs/team.md`. אל תמציא.

### 4. אמת ודווח

```bash
ls <target>/docs/journal <target>/docs/sessions <target>/progress <target>/specs
grep -rl "{{" <target> || echo "no leftovers"
```

דווח למשתמש: מה נוצר, שתי ההנחות המרכזיות שהנחת, ומה הצעד הבא (רישום
צוות ב-`docs/team.md`, spec ראשון ב-`specs/0003-...`). **אל תבצע קומיט**
אלא אם התבקשת.

## B. עבודה בפרויקט קיים

`AGENTS.md` של הפרויקט הוא המקור. הסקיל רק מזכיר את הזרימה.

### לפני כל עבודה

קרא, בסדר הזה: `progress/status.md` · `docs/journal/00-tracking.md` ·
`issues/README.md` · רשומות היומן של היום ואתמול · `docs/journal/discussions.md`.
רשום את עצמך בטבלת המעקב על הקבצים שתערוך.

### בקשה לבנות רכיב חדש

**לא כותבים קוד.** הסדר:

1. **issue** — אם אין: `issues/NNNN-slug.md` מהתבנית. עדכן את האינדקס
   ב-`issues/README.md`. המספר: הבא הפנוי בפרויקט
2. **spec** — `specs/NNNN-slug.md` מהתבנית, אותו מספר. מלא: למה קיים, מה
   עושה, קלט, פלט, מקרי קצה, מה אסור, איך יודעים שעובד, מה מחוץ לתחום,
   שאלות פתוחות. שדה "מאשר" נשאר **ריק**
3. **עצור.** הצג לאדם את ה-spec ואת השאלות הפתוחות. בקש אישור. **אין
   המשך בלי שהאדם כתב את שמו בשדה "מאשר"** או אישר בצ׳אט, ואז אתה ממלא
   את השדה ומצטט את האישור ברשומת הסשן
4. **plan** — `plans/NNNN-slug.md`, אותו מספר: צעדים, קבצים, סיכונים, איך
   בודקים. **עצור שוב** לאישור אם התוכנית נוגעת ביותר מקובץ או שניים
5. **קוד + בדיקות** — מול ה-spec. הבדיקות נגזרות מסעיף "איך יודעים שהוא
   עובד". קוד לימודי מקבל הערות מסבירות
6. **סגירה** — ראה "סוף סשן"

### spec טוב — רשימת בדיקה

- [ ] מישהו שלא ראה את הצ׳אט מבין מה הרכיב עושה מהמסמך בלבד
- [ ] לכל קלט יש טיפוס, חובה/רשות ודוגמה
- [ ] יש לפחות מקרה קצה אחד ושגיאה אחת עם התנהגות מוגדרת
- [ ] סעיף "מה אסור" אינו ריק
- [ ] סעיף "איך יודעים שעובד" מכיל דוגמה תקינה ודוגמה שגויה, שאפשר להפוך לבדיקה
- [ ] סעיף "מה מחוץ לתחום" אומר במפורש מה **לא** בונים
- [ ] אין בו שמות ספריות או מבנה קבצים. זה שייך ל-plan

### בקשה לתקן באג

issue, לא spec. אם התיקון משנה התנהגות מתועדת ב-spec — עדכן את ה-spec
קודם (שורה ב"היסטוריית שינויים"), בקש אישור מחדש, ורק אז תקן.

### בעיה מחוץ לתחום שלך

פתח issue. אל תתקן. הודע לבעל התחום ב-`discussions.md`.

### סתירה בין הוראות

בין מסמכים, או בין מסמך לבקשה בצ׳אט — עצור ודווח לאדם. ההכרעה שלו
נרשמת ב-`docs/decisions/NNNN-slug.md` עם החלופות והנימוק.

### סוף סשן — רשימת חובה

1. `docs/journal/YYYY-MM-DD-NN-slug.md` — מה נעשה ולמה
2. `docs/sessions/YYYY-MM-DD-NN-<person>-<agent>-slug.md` — מה נאמר: בקשות
   בלשון האדם, החלטות, **הנחות שהנחת בלי לשאול**, מה לא נעשה ולמה, פתוח
3. `progress/status.md` — הזז שורות, עדכן תאריך ומי
4. `issues/` — סגור מה שנפתר (קישור ליומן), פתח מה שגילית, עדכן אינדקס
5. `plans/` — סמן צעדים, "סטייה מהתוכנית" אם הייתה
6. `docs/decisions/` — אם הוכרעה בחירה בין חלופות
7. `docs/journal/discussions.md` — למי שצריך לדעת
8. שחרר קבצים ב-`docs/journal/00-tracking.md`
9. קומיט **רק אם האדם ביקש**

## קבצי הסקיל

| נתיב | תפקיד |
|---|---|
| `scripts/scaffold.py` | מקים את השלד. Python 3, ספרייה סטנדרטית בלבד |
| `templates/` | כל קבצי השלד עם placeholders בפורמט `{{NAME}}` |
| `README.md` | התקנה, שימוש ידני, איך משנים את התבניות |

לשינוי בכללים: ערוך ב-`templates/` ולא בפרויקט מוקם. תבניות עם `DATE-01-`
בשם מקבלות את תאריך ההקמה.
