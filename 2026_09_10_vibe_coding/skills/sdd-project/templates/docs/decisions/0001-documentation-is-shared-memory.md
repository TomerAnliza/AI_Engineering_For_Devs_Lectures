## הקשר

הפרויקט משותף לכמה בני אדם ולכמה סוכני AI. לכל אדם יש צ׳אט משלו עם הסוכן
שלו, ואף אחד אחר אינו רואה אותו. סוכן שנפתח מחדש אינו זוכר את הסשן הקודם.
בלי מנגנון משותף, החלטות ובקשות חיות רק בצ׳אט שנסגר, והצוות סובל מדריסה,
מחזרה על עבודה ומסתירות שקטות. ובנוסף: סוכן שמקבל "תבנה X" מנחש דרישות
שלא נאמרו, והניחוש מתגלה רק אחרי שמישהו בנה על הקוד.

## החלופות שנשקלו

1. **לא לתעד, לסמוך על Git.** ה-diff מראה *מה* השתנה אבל לא *למה*, לא מה
   נדחה, ולא מה הסוכן הניח. חיסרון: הזיכרון המשותף מתרוקן ממה שחשוב
2. **תמלילי צ׳אט מלאים.** אף אחד לא קורא אלף שורות; מידע שאי אפשר למצוא
   שווה למידע שאין. סיכון לסודות שמצוטטים
3. **כלי חיצוני** (GitHub Issues, Projects). הסוכנים לא קוראים אותו
   אוטומטית, והמידע יוצא מה-repo
4. **חמישה ערוצים בתוך ה-repo, כל אחד עונה על שאלה אחת:** `progress/`
   (איפה), `issues/` (מה שבור), `specs/` (מה בדיוק לבנות), `plans/` (איך),
   `docs/` (מה נעשה, מה נאמר, למה). וכלל: אין קוד בלי spec מאושר

## הבחירה

חלופה 4. הכלל בניסוח אחד: **מה שלא כתוב במסמך — לא קרה.** והזרימה:

```text
issues → specs → plans → קוד + בדיקות → docs/journal → progress
```

## הנימוק

העומס של חלופה 4 הוא כמה דקות בסוף סשן. העלות של האחרות היא סוכן שבונה
מחדש משהו קיים, או אדם שמגלה אחרי שבוע שהקוד מכיל שתי החלטות סותרות.
הדקות זולות מהשבוע.

spec לפני קוד הופך את הניחוש של הסוכן לטקסט שאדם קורא ומאשר **לפני** שיש
קוד לתקן.

## השלכות

- כל סשן עם סוכן מסתיים ברשומת יומן, רשומת סשן ועדכון `progress/status.md`
- קומיט קוד בלי רשומת יומן הוא קומיט לא שלם
- סוכן שמתבקש לכתוב קוד לרכיב בלי spec מאושר — כותב spec ועוצר
- מספר רץ אחד לנושא עובר בין `issues/`, `specs/` ו-`plans/`
