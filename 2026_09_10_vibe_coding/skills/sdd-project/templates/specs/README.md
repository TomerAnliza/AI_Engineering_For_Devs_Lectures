# specs — הדרישות, לפני הקוד

**Spec Driven Development.** לפני שיוצרים מערכת, קוד או רכיב תוכנה, כותבים
תיאור ותיעוד של הדרישות ממנו. הקוד נכתב מול המסמך, לא להפך.

## הבעיה שזה פותר

סוכן שמקבל "תבנה לי API" בונה משהו. הוא מנחש את הקלט, את הפלט, את מקרי
הקצה ואת מה שאסור. הניחוש נראה סביר, ומתגלה כשגוי רק אחרי שהקוד קיים
ומישהו אחר כבר בנה עליו. עם צוות של כמה אנשים וכמה סוכנים, כל אחד מנחש
אחרת.

מסמך דרישות הופך את הניחוש לטקסט שאדם קורא ומאשר **לפני** שיש קוד לתקן.

## הכלל

> **אין קוד בלי spec מאושר.** רכיב, מודול, endpoint, פונקציה ציבורית —
> כל דבר שמישהו אחר יקרא לו — מתחיל במסמך דרישות שאדם אישר.

תיקון באג בקוד קיים לא צריך spec חדש. הוא צריך issue. אבל אם התיקון משנה
את ההתנהגות המתועדת, ה-spec מתעדכן קודם.

## מה יש ב-spec ומה אין

| כן | לא |
|---|---|
| **מה** הרכיב עושה | **איך** הוא עושה את זה. זה ב-`plans/` |
| קלט, פלט, מקרי קצה, שגיאות | שמות משתנים, מבנה קבצים |
| מה **אסור** לו לעשות | ספריות, אלא אם הן חלק מהדרישה |
| איך יודעים שהוא עובד: דוגמאות שאפשר להפוך לבדיקה | הקוד עצמו |

## שם הקובץ

```text
specs/NNNN-slug.md
```

מספר רץ ארבע-ספרתי לכל הפרויקט. אותו מספר עובר ל-`plans/` שמממש אותו.

## מחזור החיים

| סטטוס | משמעות |
|---|---|
| טיוטה | נכתב, לא אושר. **אסור להתחיל קוד** |
| מאושר | אדם קרא ואישר. מותר לכתוב תוכנית ואז קוד |
| ממומש | יש קוד שעונה על כל הדרישות, ובדיקות שמוכיחות |
| הוחלף | spec חדש מחליף אותו. מפנה אליו |

spec שהשתנה אחרי אישור: הסעיף "היסטוריית שינויים" מקבל שורה, והאדם מאשר
מחדש. spec לא נמחק.

## הזרימה המלאה

```text
issues/  →  specs/  →  plans/  →  קוד + בדיקות  →  docs/journal/  →  progress/
 הבעיה      הדרישות     הדרך         הביצוע           מה נעשה         איפה זה עומד
```

`docs/sessions/` מתעד את הצ׳אט שבו כל שלב נדון. `docs/decisions/` מתעד
הכרעות בין חלופות שעלו בדרך.
